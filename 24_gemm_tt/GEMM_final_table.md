# SGEMM 九版本对比表（S2 阶段收尾）

## 测试环境

| 项 | 值 |
|---|---|
| GPU | NVIDIA GeForce RTX 4070 Laptop，Compute Capability 8.9 |
| SM 数量 | 36 |
| 显存 | 8.0 GB，带宽 256.0 GB/s（理论峰值） |
| L2 Cache | 32768 KB |
| 每 SM 共享内存 | 100 KB |
| 每 SM 寄存器 | 64 K |
| 最大线程/块 | 1024 |
| 编译参数 | nvcc -O3（未指定 -arch，使用默认目标） |
| 测量方法 | 预热 2 轮，交错测量 5 轮取最快 |

| v3_tt4 | 0.342 | 6278.9 | 3.98x | 4×4 线程分块，标量访存 |
| v4_tt4v | 0.327 | 6574.1 | 4.17x | 4×4 + float4 访存 |
| v5_tt4v_lb4 | 0.309 | 6945.6 | 4.40x | 4×4 + float4 + launch_bounds(256,4) |
| v6_tt8v | 0.337 | 6378.6 | 4.04x | 8×8 线程分块 + float4 |
| **v7_db** | **0.260** | **8256.5** | **5.23x** | 4×4 + float4 + 双缓冲 |
| v8_db_lb4 | 0.274 | 7825.2 | 4.96x | 双缓冲 + launch_bounds(256,4) |

| 版本 | 耗时(ms) | GFLOP/s | 相对 v2 | 手法 |
|---|---|---|---|---|
| v2_tiled16 | 10.780 | 1593.7 | 1.00x | 共享内存分块 TILE=16 |
| v3_tt4 | 2.223 | 7729.2 | 4.85x | 4×4 线程分块 |
| v4_tt4v | 2.125 | 8085.4 | 5.07x | 4×4 + float4 |

## 每一刀的收益

| 步骤 | n=1024 | n=2048 | 手法 |
|---|---|---|---|
| v2 → v3 | +298% | +385% | 线程分块 1×1 → 4×4 |
| v3 → v4 | +4.7% | +4.6% | 标量访存 → float4 |
| v4 → v5 | +5.6% | +7.5% | 占用率 50% → 67% |
| v5 → v7 | +18.9% | +18.6% | 加双缓冲 |
| v5 → v6 | −8.2% | −9.6% | 换成 8×8 |
| v7 → v8 | −5.2% | −6.5% | 双缓冲再压寄存器 |

## 七条结论

**一，最大的收益集中在第一步。**线程分块从 1×1 到 4×4，涨了近四倍，后面所有步骤加起来才再涨 60%。这符合分块优化的普遍规律。

**二，v7 是所有版本里最快的。**n=2048 时 10311.7 GFLOP/s，是分块版的 6.47 倍，按 20 TFLOPS 峰值估算约占 52%。

**三，矩阵越大越快。**同一个版本，2048 普遍比 1024 快 20% 以上。原因是 1024 只有 256 个 block（tile=64），36 个 SM 分不满，尾部还有空转；2048 有 1024 个 block，能排满好几轮，尾部损耗摊薄。

**四，8×8 在这张卡上不合适。**v6 在两个尺寸都输给 v5，分别低了 8.2% 和 9.6%。原因有两个：128 个寄存器只能放 2 个 block，占用率掉到 33%；以及 `Bs` 的地址间隔变成 8 个 float，bank conflict 从 2 路升到 4 路。

**五，双缓冲是第二步大收益。**+18.6%，比 float4 和占用率两项加起来还多。省下的不是带宽（DRAM 只占 2.76%），是 `__syncthreads()` 那一段的停顿。

**六，压寄存器会害了预取。**v8 强制 4 块，把寄存器从 80 压到 64，结果比 v7 慢 6.5%。双缓冲本身要 8 个寄存器做预取中转，压了就超预算。

**七，编译参数的影响大于后期优化。**同一份 v7 代码，加 `-arch=sm_89` 之后从 10311.7 掉到 9295.8，差 8%。而 v4 之后的每一步优化都在 3% 到 19% 之间。也就是说，参数没固定住的时候，测出来的优化收益是不可信的。

## 一个未解的问题

`-arch=sm_89` 让编译器普遍多要 8 到 14 个寄存器，128×128 那个版本还出现了 12 字节 spill。这解释了为什么它变慢，但 v7 在两个参数下的寄存器数看起来都在「3 个 block」的区间，占用率理论没变，所以那 8% 还有别的原因。

要追到这一层需要反汇编对比 SASS 的指令数和调度顺序。考虑到收益量级已经小于这个差异，暂时搁置。

## 复现方式

```bash
nvcc -O3 -Iinclude -Xptxas -v -o 24_gemm_tt/gemm_bench 24_gemm_tt/gemm_bench.cu
./24_gemm_tt/gemm_bench | tee 24_gemm_tt/gemm_final.txt
```

注意：`gemm_cpasync.cu` 必须加 `-arch=sm_89` 才能编译（cp.async 是 sm_80 之后的指令），所以它的数字不能和上表直接比较。
